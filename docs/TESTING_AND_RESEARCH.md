## 1. Автотесты

### 1.1 Как устроено

- **Vitest 3** + **supertest**: приложение Express поднимается внутри процесса, без сети.
- **Реальная MySQL**: отдельная БД `naryad_test` в том же контейнере, что и рабочая. Перед каждым тестом выполняется `TRUNCATE` всех таблиц и создаётся минимальный набор данных (2 участка, 3 единицы оборудования, сотрудники всех ролей, шифры, материалы, норматив).
- **Моки внешних сервисов — настоящие HTTP-серверы** (`test/helpers/mocks.ts`): Ollama, Whisper и 1С поднимаются на случайных портах. Поэтому проверяются реальные `fetch`, multipart, заголовки и коды ответов, а каждый тест задаёт свой ответ модели.
- Файлы тестов пишутся во временный каталог (`process.chdir`), рабочие `uploads/` не затрагиваются.
- Для фото генерируются **синтетические сцены**: SVG → JPEG через sharp, по разному «оборудованию» на каждое значение seed.
- Известные дефекты оформлены как `it.fails(...)`: тест описывает **правильное** поведение и сейчас падает. Набор остаётся зелёным, а после исправления дефекта Vitest подскажет снять пометку.

```bash
npm test               # все тесты
npm run test:coverage  # с покрытием (coverage/)
```

Тестам нужна БД `naryad_test` (создание описано в разделе 9) и `.env` с `MYSQL_PASSWORD`. Другой адрес БД задаётся через `TEST_DATABASE_URL`.

## 2. R1 — качество AI-проверки закрытия

**Вопрос:** отличает ли `gpt-oss:20b` нормальный отчёт исполнителя от отписки, невыполненной работы или опасного обхода?

**Методика.** 24 размеченных кейса: 12 «принять» и 12 «на доработку» по 8 типам нарушений, по 3 прогона каждого, всего 72 вызова. Наряды создаются в отдельной БД `naryad_research` и проходят **реальный** `reviewWorkOrder`. Обязательные поля заполнены, фото до и после разные, поэтому пост-правила не вмешиваются и измеряется именно LLM. Метка `accepted` — это любой вердикт, кроме `REWORK_REQUIRED`.

Сравнивались три варианта:
1. **только правила**: Ollama недоступна, работает детерминированный fallback;
2. **текущий промпт** из `src/services/ai-review.ts`;
3. **улучшенный промпт** (`research/r1b-prompt-ab.ts`) с явными критериями доработки и требованием отвечать по-русски. Данные на входе те же.

![Качество AI-проверки](img/ai-review-quality.png)

| Метрика | Только правила | Текущий промпт | Улучшенный промпт |
|---|---|---|---|
| Точность | 50.0% | 77.8% | **98.6%** |
| Найдено плохих отчётов (recall) | 0% | 58.3% | **97.2%** |
| Точность пометки «на доработку» (precision) | — | 95.5% | **100%** |
| Хорошие отчёты, ошибочно отправленные на доработку | 0% | 2.8% | **0%** |
| Один и тот же вердикт во всех 3 прогонах | 100% | 79.2% | **95.8%** |
| Время, p50 / p95 | 0.07 с | 5.7 / 7.6 с | 4.2 / 5.9 с |

![По типам отчётов](img/ai-review-by-kind.png)

| Тип отчёта | Текущий | Улучшенный |
|---|---|---|
| полный отчёт (11 кейсов) | 97% | 100% |
| краткий, но по существу («Заменил подшипник, шум пропал») | 100% | 100% |
| **пустая отписка** («Сделано», «Всё ок», «Работа выполнена») | **0%** | 100% |
| работа не выполнена («Не успел, доделаю завтра») | 83% | 100% |
| не относится к задаче | 100% | 100% |
| **нет действий** («Посмотрел, вроде нормально») | **33%** | 100% |
| проблема не устранена | 100% | 100% |
| **нарушение безопасности** («Отключил защиту, двигатель работает») | **33%** | 67% |
| мусор («asdf jkl») | 67% | 100% |
| нарушение технологии («Залил воду вместо масла») | 100% | 100% |

![Время проверки](img/ai-review-latency.png)

**Выводы**

- Текущий промпт **ни разу не вернул чистый `ACCEPTED`**: 50 из 72 ответов — `ACCEPTED_WITH_COMMENTS`. Модель цепляется за фразу эвристики фото «требуется проверка мастером» и при этом пропускает отписки.
- **36% объяснений (26 из 72) написаны по-английски**: промпт не задаёт язык.
- Только правила без LLM принимают всё, у чего заполнены поля: точность 50%, плохие отчёты не ловятся вовсе. Значит, LLM действительно даёт пользу.
- Улучшенный промпт закрывает почти все проблемы, но «отключил защиту» ловится только в 2 из 3 прогонов. Для нарушений безопасности нужно **жёсткое правило по ключевым словам** («отключ… защит», «перемыч…», «без заземл…»), а не только LLM.
- **Рекомендация:** заменить системный промпт в `ai-review.ts` текстом `PROMPT_B` из `research/r1b-prompt-ab.ts`, добавить в пост-правила проверку безопасности и требовать `REWORK_REQUIRED` при `confidence` ниже порога.

## 3. R2 — классификатор намерений AI-помощника

**Методика.** 36 вопросов, по 6 на каждое из 6 намерений; 30 на русском и 6 на казахском, с перефразами без ключевых слов. Сравнивались `classify()` с `gpt-oss:20b` и тот же код без Ollama (fallback по ключевым словам).

![Классификация намерений](img/assistant-intents.png)

| | LLM | Ключевые слова |
|---|---|---|
| Всего | **83.3%** (30/36) | 30.6% (11/36) |
| Русский | 83.3% | 33.3% |
| Казахский | **83.3%** | 16.7% |
| Время, p50 / максимум | 2.8 / 7.7 с | < 1 мс |

Ошибки LLM:

| Вопрос | Ожидалось | Получено |
|---|---|---|
| Что горит по времени? | OVERDUE | ANOMALIES |
| Покажи все наряды по дробилке Д-2 | EQUIPMENT_HISTORY | SHIFT_REPORT |
| Ауысым қалай өтті? | SHIFT_REPORT | FREE_EXECUTORS |
| Где повторяются одни и те же поломки? | ANOMALIES | EQUIPMENT_HISTORY |
| Какие отказы после ППР? | ANOMALIES | EQUIPMENT_HISTORY |
| Какое оборудование в зоне риска? | FAILURE_FORECAST | ANOMALIES |

**Выводы.** LLM втрое точнее ключевых слов и понимает казахский. Ошибки — пограничные формулировки между `ANOMALIES`, `EQUIPMENT_HISTORY` и `FAILURE_FORECAST`. Промпт классификатора перечисляет только названия намерений. **Рекомендация:** добавить по 1–2 примера на каждое намерение (few-shot); ожидаемый рост — до 95%+. Fallback по ключевым словам стоит расширить словами «история», «сводка», «смена», «риск», «ремонт».

## 4. R3 — распознавание речи (Whisper large-v3)

**Методика.** 20 фраз из практики ремонта («Износ футеровки, нужна замена плит», «Порыв ленты, выполнить вулканизацию стыка», …) синтезированы четырьмя русскими голосами Piper (denis, dmitri, irina, ruslan). К каждой записи добавлен белый шум с SNR 20, 10 и 5 дБ. Итого 320 записей, отправленных на рабочий `whisper-service`. Метрики после нормализации текста (регистр, пунктуация, ё → е): WER — доля ошибочных слов, CER — доля ошибочных символов.

![Whisper WER](img/whisper-wer.png)

| Условия | WER | CER | Фраза распознана без ошибок |
|---|---|---|---|
| чисто | **16.4%** | **4.4%** | 47.5% |
| SNR 20 дБ (тихий цех) | 18.2% | 5.6% | 46.3% |
| SNR 10 дБ (работающее оборудование) | 25.8% | 8.0% | 38.8% |
| SNR 5 дБ (громкий цех) | 36.0% | 12.3% | 21.3% |

Скорость: медиана **0.62 с** на фразу, RTF 0.22, то есть в 4.6 раза быстрее реального времени. На чистой речи WER по голосам: irina 8.1%, ruslan 14.6%, dmitri 21.3%, denis 21.4%.

Типичные ошибки — **отраслевые термины**: футеровка → «лутеровка», вулканизация → «вакуанизация», роликоопоры → «ли копоры», сапун → «соком», анкерные → «танкерные». Общая лексика распознаётся почти без ошибок. Низкий CER при заметном WER означает, что ошибки в основном в окончаниях и отдельных буквах.

**Рекомендации.**
1. Передавать в Whisper `initial_prompt` со словарём терминов (футеровка, роликоопора, вулканизация, сальник, грундбукса, сапун, редуктор, ППР). Сейчас `whisper-service` такой параметр не принимает — это доработка сервиса.
2. В клиенте показывать распознанный текст для правки перед отправкой.
3. Для шумных цехов нужна гарнитура с шумоподавлением: при 5 дБ ошибочно каждое третье слово.

**Ограничение:** использовалась синтезированная, а не живая речь. Реальные голоса, акценты и реверберация цеха обычно дают WER выше; эти цифры — **нижняя граница ошибки**.

## 5. R4 — антиподлог фото (перцептивный хеш)

**Вопрос:** поймает ли система, если исполнитель вместо нового фото «после» загрузит слегка изменённое старое?

**Методика.** 80 синтетических сцен. Каждая проходит через 9 преобразований (720 пар «то же фото») и сравнивается с 3 другими сценами (240 пар «разные фото»). Используются реальные функции `fingerprint()` и `similarity()` из `photo-analysis.ts`.

![Порог](img/phash-threshold.png)

![По преобразованиям](img/phash-by-transform.png)

| Преобразование | Порог 0.98 (сейчас) | Порог 0.88 | Медианное сходство |
|---|---|---|---|
| пережатие JPEG q40 | 99% | 100% | 0.996 |
| уменьшение в 2 раза | 95% | 100% | 0.992 |
| размытие | 99% | 100% | 0.996 |
| скриншот (PNG + рамка) | 80% | 100% | 0.988 |
| **яркость +25%** | **16%** | 95% | 0.961 |
| **обрезка 5%** | **0%** | 99% | 0.945 |
| поворот 3° | 0% | 36% | 0.867 |
| обрезка 15% | 0% | 6% | 0.828 |
| зеркальное отражение | 0% | 0% | 0.617 |
| **другое фото (ложные срабатывания)** | 0% | **0%** | 0.652, максимум 0.844 |

**Выводы**

- Порог 0.98 слишком строгий: изменение яркости или обрезка на 5% полностью обходят проверку. Всего ловится **43%** подмен.
- У разных фото сходство не поднимается выше 0.844. Порог **0.88** даёт **71%** обнаружения при **0%** ложных срабатываний.
- Сравнение с фото **из других нарядов** идёт только по точному SHA-256, поэтому то же фото из прошлого наряда, пережатое мессенджером, не обнаруживается. **Рекомендация:** хранить перцептивный хеш (уже сохраняется в `Photo.metadata.perceptual`) и искать похожие среди последних фото этого же оборудования.
- Поворот, зеркало и сильная обрезка простым aHash не ловятся; для этого нужны pHash/dHash по нескольким масштабам или vision-модель.

**Ограничение:** синтетические сцены из геометрических фигур проще реальных фото оборудования. На реальных снимках одного и того же цеха разные фото будут похожи сильнее, поэтому порог стоит перепроверить на 100–200 настоящих фото.

## 6. R5 — нагрузочное тестирование

**Методика.** autocannon, рабочий экземпляр API (`:8765`, демо-данные: 500 нарядов, 18 пользователей). 7 эндпоинтов × 1, 10 и 50 параллельных соединений, по 8 секунд. Один процесс Node.js.

![RPS](img/load-rps.png)

![Задержка](img/load-latency.png)

| Эндпоинт | RPS при 10 соединениях | p50 при 1 соединении | p99 при 10 | p99 при 50 | Ошибки |
|---|---|---|---|---|---|
| `GET /health` | 2238 | 0 мс | 9 мс | 31 мс | 0 |
| `GET /references/equipment` | 1175 | 3 мс | 15 мс | 76 мс | 0 |
| `GET /analytics/failure-forecast` | 796 | 7 мс | 19 мс | 75 мс | 0 |
| `GET /analytics/dashboard` | 317 | 19 мс | 49 мс | 241 мс | 0 |
| `GET /reports/ratings` | 314 | 17 мс | 49 мс | 165 мс | 0 |
| `GET /work-orders` (200 строк) | **46** | 89 мс | 344 мс | 1829 мс | 0 |
| `POST /auth/login` | **8** | 102 мс | 2315 мс | 6538 мс | 0 |

**Выводы**

- Ошибок нет ни на одном уровне нагрузки. Для предприятия с десятками одновременных пользователей запаса хватает с избытком.
- `GET /work-orders` — самый тяжёлый запрос: 200 нарядов с фото, материалами и AI-оценками за раз, около 89 мс работы процессора. **Рекомендация:** пагинация (`limit` / `cursor`) и облегчённый список без `photos` и `materialUsages`.
- Логин упирается в **bcryptjs** — это реализация на чистом JS, она блокирует цикл событий: около 8 входов в секунду на весь сервер. **Рекомендация:** нативный `bcrypt` или `argon2` либо вынести хеширование в worker. Заодно см. SEC-1.
- API использует одно ядро из 72. При росте нагрузки — PM2 cluster или несколько реплик за nginx; для Socket.IO понадобится адаптер Redis.

| Проверка | Результат |
|---|---|
| Нарядов / в срок / вердикты | 498 / **80.3%** / 452 ACCEPTED, 46 REWORK |
| «Конвейер К-3» найден | ✅ всеми тремя применимыми детекторами: частые отказы, повторяющийся шифр, отказы после ППР |
| Всего аномалий | **51** (25 «после ППР», 25 «повторяющийся шифр», 1 «частые отказы»), из них 48 не относятся к К-3 |
| «Исполнитель 1» на последнем месте рейтинга | ✅ 55.6 при медиане 94 |
| Время поиска аномалий | 112 мс |
| Прогноз: значение 0.95 (максимум) | у 4 из 19 единиц; К-3 — 0.87 и **не в топе** |

**Выводы**

- Заложенные закономерности находятся, но **точность детекторов низкая**: 48 из 51 сигнала — шум. Частично это особенность сида (шифры и типы нарядов чередуются по модулю, так что каждая единица получает повторы). Главная же причина — абсолютные пороги: «≥ 3 одинаковых шифра за 90 дней» и «≥ 2 аварии в течение 7 дней после ППР» не учитывают общий объём. **Рекомендация:** нормировать на число нарядов и сравнивать с распределением по парку (z-оценка), а в интерфейсе показывать только важность ≥ 4.
- Прогноз завышает единицы с ростом на малых числах («3 аварии против 1» = рост 200% → 0.95) и занижает К-3 с 88 нарядами (7 против 6 → 0.87). **Рекомендация:** сглаживание Лапласа `(recent+1)/(previous+1)` и учёт абсолютной частоты; для настоящего прогноза — пуассоновская модель по истории.
- Формулы рейтингов вычисляются верно (сверено вручную в тестах) и правильно выделяют слабого исполнителя.

### Безопасность

| ID | Риск | Описание | Рекомендация |
|---|---|---|---|
| **SEC-1** | 🔴 | **Нет ограничения попыток входа при 4-значном ПИН.** На сервере измерено ~9.6 входов/с с одного соединения, поэтому все 10 000 ПИН любого логина перебираются примерно за **18 минут** | ограничение по логину и IP (например, 5 попыток → блокировка на 15 мин), журнал неудачных входов, ПИН от 6 цифр |
| **SEC-2** | 🟠 | Socket.IO-событие `work-order:changed` уходит **всем** подключённым, включая исполнителей: они получают чужие наряды целиком (описания, ФИО, оценки), хотя REST им это запрещает | отправлять в комнаты `user:<assignee>`, `role:MASTER`, `role:MANAGER` |
| SEC-3 | 🟠 | На сервере загружены демо-пользователи с ПИН `1234`, включая `admin` | сменить ПИН или удалить демо-пользователей до открытия доступа |
| SEC-4 | 🟡 | `/uploads/*` отдаётся без авторизации. Имена файлов — 128-битные случайные, перебор нереален, но ссылка на фото действует бессрочно | выдавать файлы через авторизованный эндпоинт или по подписанным ссылкам |

## 10. Ограничения исследований

- R1: 24 кейса размечены одним экспертом (автором исследования); для статистически надёжной оценки нужно 200+ реальных закрытых нарядов, размеченных мастерами. Доверительный интервал для 98.6% на 72 вызовах — примерно 92–100%.
- R3 и R4: синтетическая речь и синтетические изображения. Цифры показывают относительные эффекты (шум, порог), а не абсолютное качество на производстве.
- R5: нагрузка с той же машины, без учёта сети; одновременно на сервере работали другие сервисы.
- R6: демо-данные периодичны по построению, поэтому оценка точности детекторов пессимистична.
